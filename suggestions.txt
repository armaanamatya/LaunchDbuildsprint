Agent Graph Suggestions and Clarifications

Core thesis
- Code quality is becoming commoditized.
- The moat is idea, design, and decision-making.
- Real software development is not one linear chat. It is branching, testing alternatives, comparing outcomes, and choosing a direction.
- The product should make that branching process visible and actionable.

One-line product framing
- Do not pitch this as "an AI coding app."
- Pitch it as a branching workspace for software decisions.
- Best line:
  Instead of asking one agent for one answer, we let you explore multiple implementation paths, compare them visually, and merge the best one.

Hackathon-winning wedge
- Open one prepared repo.
- Show a root node representing the current codebase or task starting point.
- Create 2-3 child agent branches from the same task.
- Stream progress into the graph in real time.
- Compare diffs or results side by side.
- Choose one winner and merge it.

What not to build for the hackathon MVP
- Arbitrary repo selection.
- Broad GitHub auth complexity.
- PR creation.
- Multi-model routing.
- Production-grade persistence.
- Full team collaboration.

Why narrowing helps
- Judges will score visible product insight over invisible infrastructure.
- A clean, magical workflow will score better than a larger but shakier platform.
- The graph must feel necessary, not decorative.

Rubric read
- Idea is strongest when the graph is framed as a better way to explore and choose implementation paths.
- Functionality is strongest when the scope is narrowed to one reliable loop.
- UI/UX is highly winnable because the product is inherently visual.
- Presentation is strongest when the demo focuses on the problem, the branching workflow, the comparison, and the merge.

Score target if executed well
- Idea: about 7.5/8
- Functionality: about 4/5
- UI/UX: about 3.5-4/4
- Presentation: about 2.5-3/3

UI/UX direction
- Make the graph the hero, not a side widget.
- Avoid generic AI dashboard styling.
- Use a light theme first.
- Keep node states instantly readable: idle, running, done, error.
- Make branch comparison obvious.
- Make winner selection and merge feel confident and satisfying.
- Avoid purple-gradient hackathon cliches.

Demo structure
1. Coding is not linear.
2. Existing AI coding tools force one path at a time.
3. This product lets you branch into multiple real implementation paths.
4. Show one task explored three ways.
5. Compare outputs and explain why one branch wins.
6. Merge the winning branch.

Decision log

Q1. Local only or hosted?
- Final answer: eventual hosted private alpha, not all-on-Vercel production.
- Important clarification: the issue is not whether only 3 people use it. The issue is whether the architecture supports persistent repos, worktrees, long-running agents, and safe execution.

Q2. Should frontend and backend be split?
- Final answer: yes.
- Recommended architecture:
  frontend on Vercel
  backend API and workers on Railway, Fly.io, Render, or a VPS
  Postgres for state
  Redis/Upstash or a DB-backed job table for queueing
  GitHub App preferred for hosted auth

Q3. What is the hero use case?
- Final answer:
  primary story = multiple implementations of the same feature
  expansion story = manage many active branches across different features
- Important clarification: comparison is the part that feels like a new product category. Branch management is useful, but it should be the secondary story.

Q4. Prepared repo or arbitrary repo?
- Final answer: prepared repo plus preselected task.
- Why:
  more reliable
  easier to control agent variance
  clearer diffs
  easier reset between demos

Q5. Backend-first or frontend-first hero task?
- Final answer: backend-first.
- Why:
  more deterministic
  easier to test
  easier to create multiple plausible implementations
  cleaner comparisons

Q6. What is the right demo substrate?
- Final answer: a purpose-built simple local web app.
- Recommended stack:
  tiny React frontend
  small FastAPI backend
  SQLite database
  seeded data
  pytest suite
  reset script

Q7. What is a hero task?
- Final answer: the one carefully chosen coding problem used in the demo to prove the product.
- It should be:
  small enough to finish reliably
  real enough to matter
  open-ended enough for multiple valid implementations
  different enough that branch comparison is visually obvious

Prepared demo repo recommendation
- Build a tiny support inbox or issue tracker app.
- Keep it small:
  2-3 screens
  3-5 backend endpoints
  one auth-like endpoint
  one list/search endpoint
  one mutate endpoint such as reply, resolve, archive, or comment

Recommended hero task family
- Add rate limiting to an endpoint.
- Add caching to a summary or search endpoint.
- Refactor auth middleware.

Strongest default hero task
- Add rate limiting to a real API endpoint in the prepared app.
- Good endpoint options:
  POST /api/login
  POST /api/tickets/{id}/reply

Example implementation spread for rate limiting
- Branch A: route-local implementation.
- Branch B: shared dependency or decorator.
- Branch C: reusable middleware or utility-backed implementation.

Best pitch hierarchy
- Primary story: compare branches for the same task and pick the best path.
- Secondary story: manage many agent branches across different tasks in one visual workspace.

How to stay custom while using Claude Agent SDK
- Treat the SDK as the execution engine inside each node, not as the product.
- Keep the product-owned layer around it:
  graph orchestration
  worktree lifecycle
  branch comparison
  merge and eval workflow
  issue packet generation
  auditability and policy
  frontend event model
- Use the SDK's customization surface:
  system prompts
  hooks
  permissions
  sessions
  subagents
  MCP/custom tools
  `.claude/` skills and memory
- Wrap the SDK behind your own internal runner interface so Anthropic is a backend, not the whole architecture.
